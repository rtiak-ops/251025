# BizFlow: 面接対策・技術Q&A集

このドキュメントは、プロジェクト「BizFlow」に関する技術的な質問とその回答例をまとめたものです。ポートフォリオとしての解説や面接準備に活用してください。

---

## 🏗️ 1. システム設計・アーキテクチャ

### Q: なぜマルチテナント方式として「共有スキーマ・行レベル分離」を採用したのですか？
**A:**  
本プロジェクトでは、運用コスト（RDS費用）と開発の複雑さ、そしてスケーラビリティのバランスを考慮してこの方式を選択しました。
- **コスト効率:** 全テナントで1つのデータベース・スキーマを共有するため、AWS RDSのインスタンス数を最小限に抑えられ、スタートアップ初期や小規模SaaSにおいて非常に経済的です。
- **実装の安全性:** 全ての主要テーブルに `organization_id` を持たせ、APIの共通処理（依存性注入）で `current_user` に紐づく組織IDのみを抽出するWHERE句を強制的に適用しています。これにより、物理的に別データベースにしなくても、論理的に強固なデータ隔離を実現しています。

### Q: AWS構成（S3 + CloudFront + EC2 + RDS）を選んだ理由は？
**A:**  
現代のモダンなWebアプリケーションのデファクトスタンダードに近い構成を採用しつつ、各層の責務を明確にするためです。
- **フロントエンド:** Viteでビルドされた静的ファイルをS3に配備し、CloudFrontを通じて配信することで、世界中からのアクセスに対して低レイテンシかつ安価な配信が可能です。
- **バックエンド:** EC2上でDockerコンテナを動かすことで、将来的なECS（Fargate）やEKSへの移行を容易にしています。
- **データベース:** マネージドサービスであるRDSを採用し、マルチAZ構成や自動バックアップなどの可用性を担保しています。

## 🐍 2. バックエンド (Python / FastAPI / SQLAlchemy)

### Q: FastAPI を選定した理由は何ですか？
**A:**  
主に3つの理由があります。
1. **高いパフォーマンス:** Pythonの非同期処理（AsyncIO）をネイティブにサポートしており、I/O待ちの多いWebアプリケーションにおいて優れたスループットを発揮します。
2. **型安全性とDX:** Python 3.10+ の型ヒントとPydanticをフル活用することで、APIの入出力バリデーションが自動化され、堅牢なコードを素早く書くことができます。
3. **自動ドキュメント化:** 実装と同時にSwagger UI（OpenAPI）が生成されるため、フロントエンド開発者との連携が非常にスムーズでした。

### Q: パフォーマンス監視として実装した「スロークエリ検知」について教えてください。
**A:**  
開発および運用時にデータベースのボトルネックを早期に発見するため、SQLAlchemyのイベントリスナー（`event.listens_for`）を利用した仕組みを自作しました。
- クエリ実行直前（`before_cursor_execute`）と実行直後（`after_cursor_execute`）のタイムスタンプの差分を計算します。
- 予め設定した閾値（本プロジェクトでは0.1秒）を超えた場合、実際に発行されたSQL文とパラメータをログ（Warningレベル）に出力します。これにより、インデックスの貼り忘れやN+1問題の発生を即座に特定できます。

## ⚛️ 3. フロントエンド (React / TypeScript)

### Q: TanStack Query (React Query) を導入した最大のメリットは何ですか？
**A:**  
サーバー状態のマニュアル管理（ReduxやuseContextでの複雑なフラグ管理）から解放されたことです。
特に本プロジェクトでは**「楽観的UI更新 (Optimistic Update)」**を実装しました。ユーザーがタスクのステータスを変更した際、APIからのレスポンスを待たずにUI上のキャッシュを即座に書き換えることで、ネットワークの遅延をユーザーに感じさせない「デスクトップアプリのようなサクサクとした操作感」を実現しています。

### Q: TypeScript を採用したことで、どのような開発上の恩恵がありましたか？
**A:**  
バックエンドのPydanticモデルとフロントエンドの型定義を一致させることで、APIの仕様変更に伴うエンバグをビルド時に未然に防ぐことができました。特にタスクの優先度（Priority）やステータス（Status）などの列挙型（Enum）を安全に扱えるため、コードの可読性と保守性が大幅に向上しました。

## 🛡️ 4. セキュリティ・品質管理

### Q: 監査ログ (Audit Log) はどのような目的で、どう実装されていますか？
**A:**  
B2B（エンタープライズ）向けSaaSとして、「誰が・いつ・何を変更したか」の証跡を残すことは必須要件です。
- **目的:** データの不正操作の検出や、意図しない変更が行われた際の調査、コンプライアンス要件の充足。
- **実装:** `todos` や `projects` の作成・更新・削除のロジック（CRUD層）に、監査ログテーブルへの挿入処理を組み込んでいます。管理者は専用のダッシュボードから、組織内のすべての操作履歴をフィルタリングして閲覧できます。

### Q: セキュリティ対策（脆弱性診断など）はどのように行っていますか？
**A:**  
CI/CDパイプライン（GitHub Actions）に脆弱性スキャナの **Trivy** を組み込んでいます。
- コードが `push` されるたびに、使用しているOSのパッケージやPython/npmライブラリに既知の脆弱性がないかを自動スキャンします。これにより、重大な脆弱性を抱えたままデプロイされるリスクを最小限に抑えています。

## 🤖 5. AI統合 (Generative AI)

### Q: Google Gemini API を活用した「タスク分解機能」について説明してください。
**A:**  
ユーザーが入力した曖昧なタスク（例：「新しいプロジェクトの企画」）を、具体的な実行ステップに分割する機能です。
- **プロンプトエンジニアリング:** AIに対して「JSON形式で返却すること」「タイトル・詳細・優先度・期限の4つの項目を持たせること」を指示するシステムプロンプトを設計しました。
- **プロセッシング:** 生成されたJSONをパーズし、エラーハンドリングを行った上で、データベースに一括登録するバッチ処理的なフローを実装しています。生成AIを「チャット」ではなく「ワークフローの自動化」として活用しているのが特徴です。

## 🚀 6. 開発プロセス & DevOps

### Q: インフラを Terraform でコード化（IaC）した理由は何ですか？
**A:**  
インフラの「再現性」と「可視性」を確保するためです。
- AWSコンソールでの手動操作は手順書が必要になり、ミスも起きやすいですが、Terraformであれば `main.tf` などのコードを見るだけで構成がわかります。
- また、開発（Dev）環境と本番（Prod）環境を同じコードから（変数の切り替えだけで）構築できるため、環境ごとの差異によるトラブルを防ぐことができます。
